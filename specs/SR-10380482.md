## 2. Business objective and scope

### Objective and users

New vendor codes integrated from SPPM to SAP must receive payment term `P030`
instead of default `P000`, regardless of an incoming creation payment term.
Updates must retain the vendor's existing SAP payment term.

As a business user responsible for vendor integration, I want newly created
vendors to receive `P030` so that the required default is applied without
changing existing vendors' payment terms during updates.

### In scope

- Analyze the shared payment-term assignment in ZIS candidate `ZISMD_ZAPVNDRINTF`.
- Propose changing the relevant `gs_lfb1-zterm` literal from `P000` to `P030`.
- Preserve existing downstream update processing and unrelated behavior.
- After explicit confirmation of the exact design and scope, route any approved
  source change through the ABAP source-write owner for the confirmed ZIS
  object/system; the SDD author does not directly edit SAP source.
- Prepare developer test scenarios and record references to actual evidence
  supplied by developers; AI must not execute programs or tests.

### Out of scope

- Modifying original reference object `ZAPVNDRINTF`.
- Adding `LFB1` reads or creation-only branching at this assignment.
- Changing the existing `gc_crt OR gc_upd` condition.
- Globally replacing other `P000` occurrences, refactoring, or unrelated cleanup.
- AI program/test execution, transports, ALM updates, or deployment.
- Git staging, commits, or pushes without a separate explicit request.
- Overwriting unrelated developer changes.

## 9. Acceptance criteria

### AC-1 - Creation assigns P030

- Rules: BR-001
- Given a new vendor is being created through the SPPM-to-SAP integration,
- When creation completes successfully,
- Then the resulting SAP payment term is `P030`, regardless of any incoming
  creation payment term.

### AC-2 - Update preserves the existing SAP payment term

- Rules: BR-002
- Given an existing vendor has a payment term stored in SAP,
- When an update completes successfully through the integration,
- Then the resulting payment term equals its stored value before the update,
  rather than the shared default or an incoming value.

### AC-3 - Unrelated processing is preserved

- Rules: BR-003
- Given an otherwise valid creation or update request,
- When the modified program processes it,
- Then unrelated field handling and validations continue to behave as before.

These criteria are preserved from the supplied SCR, not asserted to be the
approved ALM criteria. Developers must reconcile them before implementation.
